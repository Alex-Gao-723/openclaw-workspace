# AI原生创业指南（第三章）：MVP阶段 — 构建、测量、学习

> 翻译自 Anthropic 官方文档 *The Founder's Playbook: Building an AI-Native Startup*

## 第四章：MVP阶段

很多创始人将MVP阶段视为构建阶段，但MVP阶段本质上仍然是**证据收集练习**。区别在于，你现在是在收集关于解决方案而非问题空间的证据；具体而言，一个真实的、可识别的人群是否认为它有价值，足以使用它、回到它、为它付费，和/或告诉别人。

### MVP阶段目标

作为AI原生创业公司的创始人，你的目标是将一个已验证的问题转化为一个真实用户会实际使用的工作产品。这不是包含所有路线图功能的完整版本，而是你想法的最小、最聚焦的迭代，将一个真实的解决方案放在真实用户面前，并产生产品-市场匹配的真实证据。

同时，你当前的构建方式决定了以后可能做什么。这意味着MVP阶段有第二个同样重要的目标：**快速移动而不积累会复合的技术债务**——这些债务会在真实用户以有意义的数量到来时困扰你。

最后，从第一天起投资于持久上下文，是让AI保持倍增器而非熵的源头。在AI原生创业公司中，你的代码库是你与AI一次接一次会话协作的东西，这使得**可读性成为基础**。跳过规格说明、架构决策和上下文文件（如CLAUDE.md）的创始人，会撞上一个可预测的墙：每次新会话都需要重新解释代码库，AI生成的变更会偏离原始愿景。

### MVP阶段退出标准

MVP阶段的退出条件是**产品-市场匹配（Product-Market Fit, PMF）的真实证据**：证明一个具体的、可识别的用户群体发现产品有价值，足以回到它（留存）、为它付费（收入）或告诉别人（推荐）。

### MVP阶段的挑战

在MVP阶段，创始人的首要指令是**速度和判断力**。这里的挑战集中在你能否构建正确的东西、用正确的方式、快到足以产生影响，而不削减以后会代价高昂的角落。

#### 挑战1：智能体技术债务

**挑战：因为AI本质上消除了曾经控制什么能进入生产环境的每一个自然瓶颈，速度是有保证的。但当速度成为创始人MVP构建中唯一考虑的因素时，他们就有积累难以偿还的技术债务的风险。**

在MVP阶段积累一些技术债务是适当的，前提是理解必须在规模化前进行管理。它逐渐积累，可以随时间清理或在专门冲刺中解决。然而，**AI技术债务会复合**。如果没有规格说明和架构约束写在AI可以读取的地方，每次会话从头重新推导基础决策，这些决策就会漂移。你最终得到的代码库背后没有连贯的心智模型，不是因为任何单个部分不好，而是因为各部分从未设计为协同工作。这是真实的问题，它确实倾向于很晚才浮现。

而且，从第一天起投资于持久上下文，是让AI保持倍增器而非熵的源头。在AI原生创业公司中，你的代码库是你与AI一次接一次会话协作的东西，这使得可读性成为基础。跳过规格说明、架构决策和上下文文件（如CLAUDE.md）的创始人，会撞上一个可预测的墙：每次新会话都需要重新解释代码库，AI生成的变更偏离原始愿景。

#### 挑战2：虚假的产品-市场匹配

**挑战：AI工具可以产生令人印象深刻的早期数字，但这些并不保证市场需要你的产品。**

早期动力是创始人能拥有的最具心理力量的体验之一。经过数周或数月的验证工作和谨慎、有纪律的构建，交付产品感觉像是确认你一直都是对的。

智能体编码工具可以帮助你比以往任何时候都更快地达到这一刻，但**早期牵引力不等于产品-市场匹配**。发布能量来自短暂的力量：创始人的朋友、投资人其他投资组合公司的潜在买家、或者驱动一波高峰的Hacker News标题。不幸的是，这些都无法可靠预测第六周或第十二周初始高峰消退后会发生什么。

#### 挑战3：零摩擦的功能蔓延

**挑战：当构建感觉轻松且近乎免费时，总有一个更酷的功能要添加或一个边缘情况要处理。这种功能蔓延可能弊大于利。**

功能蔓延一直是创业风险。现在的区别在于，传统的对抗力量——工程时间的真实成本——当添加一个功能只需要一个下午而非一个冲刺时，不再以相同方式存在。

这里的挑战是每个单独的添加都是可防御的。产品当然应该处理那个边缘情况；用户当然会想要那个工作流。这些在那一刻感觉不像功能蔓延，因为每个用智能体编码构建只需很少努力，但随着你的产品蔓延超出原始边界，**你就有失去方向和动力的风险**。

解药是在开始构建之前创建的书面范围定义，描述产品做什么、**刻意不做什么**，以及来自真实用户的什么具体证据可以证明添加新东西。

#### 挑战4：经验不足导致的不安全

**挑战：使用AI工具匆忙将应用推向市场的创始人，如果不先理解基本安全原则，最终会将其用户暴露于可预防的风险。**

残酷的事实是，智能体编码工具生成的是**能工作的代码，而非天生安全的代码**。功能代码容易，因为功能要么工作要么不工作。安全漏洞在被利用之前是隐形的，这意味着没有自然反馈循环来提醒首次创始人有什么地方不对。然而，将实时MVP发布给真实用户意味着真实数据、真实暴露，以及如果出错的真实后果。

轻视安全对AI原生项目来说并不新鲜。自力更生的创业公司在每个时代都经常将安全考虑推迟到构建后期，有时等到生产发布前夕。在真实用户触及你的应用或解决方案之前进行安全审查，是将最小可行产品发布到世界的最低责任门槛。

### Claude如何帮助MVP阶段创始人

#### 在构建前定义架构

在Claude Code写一行生产代码之前，使用Claude定义和记录将管理此阶段构建的一切的架构决策：要遵循的模式、要避免的依赖、以及此时有意识接受的权衡。此输出将作为聚焦的架构上下文文档，并成为Claude Code将操作于其中的护栏。

没有此上下文，每次会话从头开始，Claude Code被迫推断自己的结构假设。让Claude Code在没有护栏的情况下构建，会产生功能上运行但结构上不连贯的代码库，而在不连贯的代码库上迭代和规模化最终是浪费时间和token。迟早有一个点，代码不可避免地崩溃，迫使你从头重建。

• **练习**：在打开Claude Code之前，打开Claude并描述你正在构建的东西：它解决的核心问题、服务的用户、以及未来六个月你实际预期的规模。要求它帮助你定义MVP构建应遵循的架构原则、给定约束下应避免哪些依赖、以及你在此阶段有意识接受的权衡。

接下来，将此输出保存为CLAUDE.md markdown文件。这是你的构建的第一个工件，也是每次后续会话依赖的工件。CLAUDE.md文件作为Claude Code的项目级指令，提供Agent SDK在目录中运行时自动读取的项目特定上下文和指令。功能上，它们是你项目的持久"记忆"。

每次Claude Code会话开始时，（1）重新审视你的范围文档和（2）向模型提供你的CLAUDE.md架构上下文文档。每次会话结束时，用它记录会话揭示的任何决策更新它。目标是结构可以解释的代码库，而非仅仅能运行的代码库。

#### 定义并执行MVP范围

没有摩擦的功能蔓延是AI时代MVP的确定性失败模式之一。正如你定义和记录了产品的应用架构一样，在构建单个功能之前你也需要定义MVP的范围。

Claude可以帮助你创建一个范围文档，描述你的MVP产品做什么、**刻意不做什么**，以及功能修订标准：此时来自真实用户的什么具体证据可以证明添加新东西。

当新功能想法浮现时——它们肯定会出现——你使用Claude来压力测试它是用户的真正信号，还是伪装成产品思维的创始人热情。

• **练习**：为你的Claude Code工作创建一个简单的会话模板，包括架构上下文文档、此会话的具体任务、以及要遵守的任何约束或模式。在每次会话结束时，添加上下文文档的简要日志条目，记录构建了什么、做出了什么决策、以及会话引入了什么假设。每次会话五分钟的文档记录是对复合成不可管理代码库的架构漂移的廉价保险。

#### 用Claude Code构建MVP

一旦架构和范围定义好，Claude Code就成为主要的MVP构建工具。用它生成、测试、调试和迭代代码库，但将每个会话视为你已经做出的产品决策的执行，而非抛出一些新决策的机会。

#### 在任何用户触及之前进行安全审查

作为AI原生创业公司创始人，你的责任是了解代码库中有什么、理解任何潜在的暴露向量，以及不向信任你其数据的真实用户发布明显的漏洞。

Claude可以对AI生成代码进行有用的第一遍安全审查，并可以帮助识别常见漏洞。在发布前将其构建到循环中是一个好习惯。然而，它不能替代安全工具，或者，在更高风险时，人工审查——那些将其视为替代的创始人，最终会出现在违规故事中。

**Claude Code Security**更进一步：它扫描代码库中的安全漏洞，并建议针对性补丁供人工审查，揭示传统方法可能遗漏的问题。

*注意：在此电子书发布时，Claude Code Security是有限测试版，请在将其构建到工作流前检查当前可用性。*

• **练习**：在部署给任何真实用户之前，通过Claude运行你的核心应用代码，并附带特定简报：审查身份验证和会话处理、API响应中的数据暴露、输入验证和注入风险、以及已知漏洞的依赖。认真对待每个发现并评估是否需要修复，对于触及身份验证、密钥或数据处理的任何问题，进行人工审查。

#### 在发布前构建测量框架

将早期牵引力误认为产品-市场匹配的创始人，通常是那些在发布后才开始跟踪数据的创始人，使用的指标被选择来评估什么在起作用，而非揭示什么不起作用。解药是在第一个用户出现之前建立测量框架。

使用Claude定义对你的特定产品重要的指标、基准是什么、以及数据中的什么模式构成真正的产品-市场匹配与令人愉悦的噪音。具体而言：在发布MVP之前设定你的留存基准、激活标准、以及第7天和第30天目标。

接下来，定义对你的特定产品来说，**假阳性是什么样子**：没有激活的注册、没有留存的收入、或没有重复使用的初始热情。当数据到来时，要求Claude对你的牵引力构建对抗性论证：怀疑者会对这些数字说什么？

#### 迭代朝向证据，而非朝向完整

无论产品感觉多"完成"，MVP阶段以产品-市场匹配的真实证据结束。声明你已经实现产品-市场匹配并准备好从MVP阶段进入发布阶段，**最终是结合创始人直觉和收集证据的判断练习**。有一些有用的试金石测试：

• **Sean Ellis测试**：问你的活跃用户："如果你不能再使用这个产品，你会感觉如何？"如果超过40%回答"非常失望"，这是有意义的PMF指标。

• **努力测试**：产品-市场匹配前，留存需要持续干预，包括频繁外联、激励、个人跟进、以及保持用户参与的英雄式创始人能量。产品-市场匹配后，产品开始自己做这项工作。当事情从推动变为拉动时，那种努力的转变是某些真实的东西已经改变的最清晰信号之一。

最终，没有单一数据点确认产品-市场匹配，因为它是必须在多个迭代周期中保持的模式，你才能明确地称之为PMF。

#### 管理发现和用户反馈物流

一旦真实用户进入产品，运营层迅速扩展。Claude Cowork处理重要但繁琐的工作，如构建和维护用户联系人列表、运行外联序列、安排反馈会话、分类bug报告和跟踪迭代周期。在创意阶段管理发现物流的相同MCP集成在此适用。

在反馈收集循环中保留人类，以深入探索用户反馈的细微差别。例如，用户说"这很棒但我希望它也能……"需要解读：它是核心需求还是锦上添花？它对这个客户特定还是代表一个细分群体？缺失的功能是真正的问题，还是入职流程中上游的问题？没有工具能回答这些问题。

• **练习**：配置Claude Cowork运行你的MVP阶段反馈循环：向早期用户列表起草外联、安排反馈会话、设计bug报告和功能请求的结构化接收流程、并撰写每周综合报告。先自己审阅综合报告；然后你可以要求Claude分析信息，以捕捉你可能遗漏的任何重要点。

#### 当证据要求时转向

即使投入了所有这些工作，如果你似乎就是无法达到产品-市场匹配呢？**你的结果不支持你开始的方向这一事实，不是失败，而是系统在工作**：MVP阶段旨在在你对错误答案过度投资之前揭示这一信息。

当数据不支持你当前的产品时，使用Claude来理解数据在告诉你什么。

• **探索替代客户细分**。也许没有转化的用户从来不是正确的目标。通常正确的受众已经在你的数据中，只是被低估了权重。

• **调整产品的价值主张**。也许你有正确的受众，但你的MVP就是没有与用户产生共鸣。调整入职流程、信息传递或核心功能重点，可能可以在不改变构建内容的情况下修复这个问题。

保持断开可能深到需要更根本性改变的可能性。

• **练习**：如果你已完成三个或更多迭代周期而没有向产品-市场匹配基准的有意义进展，使用Claude在决定下一步之前运行诊断。输入你的留存数据、用户反馈和原始问题假设，问它三个问题：
  - 数据中是否有某个细分群体与其他群体的反应不同？
  - 设计价值与体验价值之间的差距是定位问题还是产品问题？
  - 当前产品要找到真正的PMF需要满足什么条件，鉴于你看到的情况，这个场景现实吗？

让答案决定你是调整、转向还是返回创意阶段。
